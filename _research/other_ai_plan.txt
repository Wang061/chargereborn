# esp-camera-mcp.py

import cv2

@mcp.tool()

def capture_board_image() -> str:

cap = cv2.VideoCapture(0)

path = "board_debug.jpg"

return path

@mcp.tool()

def record_board_video(duration: int = 3) -> str:

cap = cv2.VideoCapture(0)

fourcc = cv2.VideoWriter_fourcc(*'mp4v')

out = cv2.VideoWriter('board_debug.mp4', fourcc, 20.0, (640, 480))

for _ in range(duration * 20):

ret, frame = cap.read()

if ret: out.write(frame)

cap.release()

out.release()

return "board_debug.mp4"

if __name__ == "__main__":

另外，ESP32-S3 用 ESP-IDF 官方体系完全没问题；Espressif 的 ESP32-S3
文档明确说明 ESP-IDF 是官方开发框架，支持 ESP32-S3
的搭建、menuconfig、build 和 flash
流程，而且官方建议生产项目优先用稳定版，再跟进 bugfix 版本。 你指定
5.5.4 很合理，我会按 5.5.x 稳定线思路来做，不碰 6.x
那些会带来迁移噪音的新变化。[github]

总体架构

这套系统我建议叫：

S3-Forge：Claude Code 驱动的 ESP32-S3 极限开发底座。[getaiperks]

设计目标只有五个：

-   单底座：只认 Claude Code，别搞双主控。[getaiperks]

-   单主线：只认 ESP-IDF 5.5.4，所有
    rules、skills、脚本都围着它转。[nxcode]

-   单闭环：需求、编码、构建、烧录、监视、诊断、修复、提交，一条链打通。[developer.espressif]

-   少冲突：只保留一个主 orchestrator、一个主 build
    流程、一个主日志分析入口。[docs.github]

-   强覆盖：把你想要的 ECC 式全功能，拆成适合嵌入式的
    skills、hooks、commands 和 MCP。[opentools]

你最终会得到的，不是一个“插件堆”，而是一个 工程操作系统。ECC
官方说明里已经把它定义成 production-ready 的 Claude Code plugin，包含
agents、skills、hooks、commands、rules 和 MCP
configs，这正好适合拿来改造成嵌入式专用版本。[getaiperks]

底座选型

底座就一个：Claude Code + ECC 思路定制版。[opentools]

为什么不是 Cursor：

-   Cursor 更适合做 IDE
    和交互壳，不是最适合做核心执行层；你现在要的是“谁来统筹构建、刷机、日志
    triage、自动流程”，不是“谁补全丝滑”。这个场景 Claude Code +
    hooks/skills/MCP 更顺手。[developer.espressif]

为什么不是 Codex：

-   Codex 适合当副脑，但你要求“底座只选一个”，那就不能让它来当
    orchestrator。它更适合未来被 Claude Code
    当外部能力或人工辅助参考，而不是系统中枢。[opentools]

为什么是 ECC 路子：

-   ECC
    的结构已经非常清楚：agents、skills、commands、hooks、rules、mcp-configs、scripts，天然适合变成一个嵌入式开发底板。[getaiperks]

-   ECC 还有 /build-fix、/plan、/code-review、/learn
    这类工作流命令思路，你完全可以移植成 ESP 版 slash
    commands。[getaiperks]

所以最终结论很简单：

底座 = Claude Code
骨架 = ECC 结构
领域 = ESP-IDF 5.5.4 + ESP32-S3

MCP 方案

这里我给你的是 最强但克制 的 MCP
组合。注意：不是装最多，而是保证闭环最完整。

必装

1.  ESP-IDF Tools MCP / 等价本地 IDF 命令 MCP
    Espressif 官方开发者门户已经明确提到 Tools local MCP server 可以让
    AI 客户端控制项目、设置
    target、build、flash、看状态，这正是你整个系统的核心能力。[developer.espressif]

2.  Filesystem MCP
    读取工程树、组件目录、sdkconfig、分区表、日志和回溯文件。

3.  Terminal MCP
    负责调用 idf.py、esptool.py、parttool.py、串口监视命令。

4.  Git/GitHub MCP
    查分支、做提交说明、PR 审查、issue 对照。

5.  Docs/Search MCP
    查 Espressif 编程指南、GitHub issue、论坛、社区案例。

选装但推荐

6.  Serial Monitor MCP
    如果你有单独可接的串口控制层，就把 monitor 从普通 terminal MCP
    里拆出来，这样更稳定。

7.  Test MCP
    跑 host test、集成测试、HIL smoke test。

不建议装太多的

-   多个重复的 shell MCP

-   多个重复的 filesystem MCP

-   多个都能 build/flash 的 ESP MCP
    因为这会导致路由歧义，Claude Code 在 tool selection
    时更容易绕路。[docs.github]

MCP 优先级

建议固定优先级：

1.  ESP-IDF MCP

2.  Terminal MCP

3.  Filesystem MCP

4.  Git MCP

5.  Docs MCP

6.  Test MCP

也就是：设备命令优先于通用命令，通用命令优先于文档检索。

Hooks 设计

GitHub 的 hooks 文档说明，hooks 非常适合拿来定制 agent
workflow，尤其适合 pre/post tool 自动化。
这对嵌入式是神兵，因为构建和刷机这种事最怕人忘步骤。[docs.github]

我建议你做下面这套 hook 链：

1. pre-session

进入会话时自动检查：

-   当前目录是不是合法工程

-   IDF_PATH 是否存在

-   Python 虚拟环境是否激活

-   idf.py --version 是否为 5.5.4

-   target 是否为 esp32s3

如果不符，直接弹出修复建议，不允许进入重度修改。

2. pre-build

构建前自动做：

-   检查 sdkconfig 是否与 esp32s3 匹配

-   检查 managed_components 是否完整

-   检查 partitions.csv 是否语法正确

-   检查 main/CMakeLists.txt、组件注册是否缺失

-   检查最近改动是否涉及 menuconfig 关键项

3. post-build

构建后自动：

-   解析 warning/error

-   归档 build log 到 logs/build/

-   分类错误为：

    -   include 缺失

    -   symbol undefined

    -   Kconfig 依赖

    -   target mismatch

    -   linker region overflow

    -   component not found

4. pre-flash

刷机前自动：

-   检测串口

-   检测占用

-   读取芯片信息

-   校验 target 是 S3

-   校验分区布局和产物大小

5. post-flash

刷机后自动：

-   记录 flash log

-   执行一次 boot smoke check

-   检测是否进入 boot loop

-   如失败，自动建议降波特率、擦写特定分区或 full erase

6. monitor-watch

监控日志时自动：

-   捕获 panic 关键字

-   自动切片保存异常窗口前后 200 行

-   提取 backtrace

-   归档到 logs/panic/

7. pre-commit

提交前自动：

-   跑 build

-   跑基础 smoke test

-   检查 sdkconfig diff

-   检查 partitions.csv 改动

-   检查是否误提交大日志、bin、密钥、证书

8. post-task

任务结束后自动输出：

-   改了什么

-   验证了什么

-   还有什么风险

-   下一步建议

Rules 设计

Rules 是“最容易被低估，但最决定系统质量”的层。ECC 明确有 rules 和 prompt
defense baseline，这种安全和边界控制对自动化 agent 很关键。[getaiperks]

你的嵌入式 rules 应该至少包括：

工程规则

-   默认只改与任务直接相关文件

-   任何涉及 sdkconfig、partitions.csv、boot、OTA、NVS
    的修改必须显式说明风险

-   任何涉及 clock、power、flash、PSRAM 的修改必须要求 build + boot
    check

编码规则

-   新增模块必须组件化，不准把所有逻辑塞 main

-   驱动与业务分层

-   日志统一 TAG 和等级

-   禁止神秘 magic number

-   ISR 中禁止做阻塞和重活

-   任务创建必须声明栈和优先级理由

验证规则

-   改功能必须 build

-   改启动路径必须 flash + boot check

-   改并发路径必须做 monitor 验证

-   改存储/分区必须做 layout 校验

防翻车规则

-   禁止自动升级 ESP-IDF 主版本

-   禁止把 target 从 esp32s3 悄悄切成别的

-   禁止未说明地 fullclean

-   禁止随便 erase_flash

-   禁止覆盖用户 board config
